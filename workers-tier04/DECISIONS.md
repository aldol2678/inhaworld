## 2. C그룹 — Realtime 대체 (C-1~C-8, 출처 C-DESIGN.md §6 D-1~D-7 + §1.5)

### C-1 — DO 도입 여부: **(b) HTTP 분리만 진행, DO는 설계만** (권고대로)
- (b) HTTP 폴링 분리안(heartbeat·온라인 수)만 구현한다. (a) Durable Objects + WebSocket 이관은 설계만 남기고 구현하지 않는다.
  presence·pose·action broadcast는 Supabase Realtime에 남는다 (이번 격리 범위에서는 손대지 않는다).

### C-2 — HTTP 폴링 간격·count 캐시: **heartbeat 20초 유지·count 캐시 5초** (권고대로)
- touch 간격 20초, 활성 윈도우 70초, count 새로고침 20초를 원본 그대로 유지한다.
  `GET /api/world-online-count`는 Worker 메모리 5초 캐시 + `asOf`는 캐시 생성 시각.
  온라인 수는 최대 25초 늦은 수를 본다 (허용).

### C-3 — heartbeat 세션 id와 게스트 세션 id 합치기 여부: **합친다** (권고대로 결정 — 문서에서는 미결정으로 남겨져 있었음)
- heartbeat 세션을 게스트 세션(`X-Session-Id`)과 동일 id로 한다. 온라인 수와 A-2 쓰기의 주체가 일치한다.
  heartbeat 모듈이 세션을 새로 만들지 않고, 세션이 없으면 heartbeat를 시작하지 않는다
  (A-2 클라이언트와 동일 원칙: 세션 없으면 `SIGNED_OUT`/`UNAVAILABLE`에 머문다. 가짜 id를 만들지 않는다).

### C-4 — 게스트 채팅·이모트 개방 범위: **현행 유지(게스트 채팅·이모트 불가)** (권고대로)
- 게스트는 pose·jump·teleport만 보낼 수 있다. 채팅·이모트는 회원 전용으로 둔다.
  DO 이관 시 채팅 속도 제한(1분 10건)은 DO 설계에 이미 적혀 있으나, 이번 구현 범위(폴링만)에서는 적용 대상이 없다.

### C-5 — 공유 NPC 스냅샷 DO 위치: **(a-1) 권고로 기록만** (권고대로 — 구현 없음)
- 스냅샷 DO가 250 ms마다 구역 DO에 푸시하는 (a-1)로 기록한다. DO 구현 착수 때 재확인한다.
  단, 구역에 관찰자가 있을 때만 푸시한다 (빈 구역에는 보내지 않음).

### C-6 — 세션 만료 시 연결 즉시 끊기 여부: **재연결 시 검사만** (권고대로)
- DO는 연결 중 세션 만료를 검사하지 않는다. 소켓이 끊기고 재연결할 때 검사한다.
  방 접근 검사의 주기적 재검사만 예외이다. 즉시 끊기를 원하면 DO 설계에 세션 재확인 주기를 추가해야 한다.

### C-7 — 외부 실시간 SaaS 검토 여부: **DO안으로 간다 (외부 SaaS 제외)** (권고대로)
- Ably·Pusher·Liveblocks 등 외부 실시간 SaaS는 검토 대상에서 제외한다. 새 외부 의존·과금·개인정보 위탁이 생긴다.
  알돌이 외부 SaaS를 명시적으로 원하면 재검토한다.

### C-8 — 공유 NPC 틱 RPC: **재구현하지 않는다 (휴면 유지)** (C-DESIGN.md §1.5 확인 사항 — §6 결정표에는 없는 항목이라 여기서 결정으로 명시)

### D-4 — 이미 있는 프로필 재요청 시: **200 기존 반환 (`created: false`)** (권고대로)
- 동일 세션 재요청 시 기존 행 그대로 반환하고 변경하지 않는다. 요청 내용이 기존과 달라도 기존 값을 반환한다
  (수정은 별도 API의 몫). 네트워크 재전송·더블탭에 안전하다. `PROFILE_CONFLICT` 코드는 쓰지 않는다.

### D-5 — 밴 프로필 재 생성 시도 시 응답: **409 `PROFILE_REQUIRED` (상태 은폐)** (선택지 중 결정 — 문서 권고 없음)
- 밴 상태를 노출하지 않는다. 생성 재시도로 밴을 우회할 수 없게 한다.
  (대안 409 `PROFILE_BANNED`는 밴 여부를 외부에 알리므로 채택하지 않는다.)

### D-6 — 프로필 수정 API 범위·시기: **생성과 분리해 후속으로** (문서 범위 명시대로)
- 이번에는 생성만 구현한다. 수정(`PATCH /api/world-profile` 등, 닉네임 변경 쿨다운 포함 여부 포함)은 D 후속 설계로 남긴다.

### D-7 — 학과 선택 범위: **active=true만** (선택지 중 결정 — 문서 권고 없음)
- `departments`에서 `active=true`인 행만 선택 가능하다. 존재하지 않거나 `active=false`면 400 `INVALID_DEPARTMENT`.
  (시드 67개 학과는 전부 `active=true`로 확인됨 — `schema.sql` 학과 시드 전수 확인.)

### D-8 — 메일 인증과 프로필 생성의 결합 여부: **선택 사항** (권고대로)
- 프로필 생성과 메일 인증을 결합하지 않는다. 메일 인증 없이도 프로필을 만들 수 있다.
  결합하면 게스트 유입이 막힌다. 메일 인증은 프로필 생성 뒤의 선택 경로이다.

### D-9 — 세션 영속성 (기기 변경 시 프로필 이관): **세션 재생성 시 프로필 재작성 (별도 이관 수단 없음)** (선택지 중 결정 — 문서 권고 없음)
- 세션 id가 바뀌면 프로필도 새로 만들어야 한다. 기존 활동 데이터(지갑·인벤토리·진행)는 `p_user` = 세션 uuid로 이미 연결돼 있어
  소실되지 않지만, **새 세션의 프로필은 새 행**이다 (구 프로필의 닉네임·학과가 자동 이관되지 않는다).
  이관 코드 등 별도 수단은 설계하지 않는다 — 세션→정식 계정 매핑이 정해지기 전에는 이관 수단의 전제가 없다.
  되돌릴 수 있는 쪽: 나중에 매핑이 정해지면 이관 경로를 그때 만든다.

## 4. 학습 (L-1~L-8, 출처 LEARNING-DECISION.md §6)

### L-1 — 학습 클라우드 저장 go/no-go: **(c) 연기** (권고대로)

### L-4 — (a) 선택 시 용량·속도 제한: **연기 상태에서 답할 수 없음 — 기록만**

### L-5 — (a) 선택 시 원본 학습 데이터 이관 여부: **연기 상태에서 답할 수 없음 — 기록만**

### L-6 — (b) 선택 시 사용자 안내: **해당 없음 (연기이므로) — 기록만**

### L-7 — 학습 콘텐츠 릴리스 일정: **연기 상태에서 답할 수 없음 — 기록만**
- 콘텐츠(`LEARNING_RELEASE`)를 언제 켤지는 저장 결정과 별개로 정해야 한다. 일정 미정.

### L-8 — (c) 선택 시 재검토 트리거: **D그룹 결정 완료** (권고대로 — 세 가지 트리거 중 하나로 확정)

  세션→유저 매핑이 정해지기 전까지 방 장비 전파가 어긋날 수 있다. 컷오버 전에 해결을 시도하고,
  해결이 안 되면 그대로 두는 것으로 기록한다 (알돌에게 알릴 사항).

### C-10 — 이중화 기간: **2주** (권고대로)
- 이관 직후 Supabase를 바로 끄지 않고 2주간 양쪽을 유지한다. 이중화 중 쓰기는 Neon으로만 하고 Supabase는 읽기 전용 백업으로 둔다.
  이중화 종료 시 Supabase를 정지·보존한다 (삭제하지 않는다 — 롤백용).

### C-11 — 전환 시간대: **사용자 적은 시간대 (구체 시각은 컷오버 단계에서 정함)** (문서대로 — 위임)
- G-8과 동일하게 컷오버 단계에서 정한다.

### C-12 — 전환 완료 선언 기준: **스모크 전부 통과 + 알돌 승인** (문서대로)
- 스모크 항목(CUTOVER-PLAN.md §⑥ ①~⑧) 전부 통과 후 알돌이 "전환 완료"를 선언해야 컷오버가 끝난다.
